[performance · low] The label for a column is invariant across all rows, but `label_for_field()` is
now called for every field of every result row (`items_for_result()` is invoked once per row). For
100-row changelists with callable/related columns this means thousands of redundant
`hasattr`/`get_field`/`pretty_name` lookups per page. Consider resolving the labels once per column
(e.g. reuse the value already computed in `result_headers()` or cache it on the changelist) instead
of recomputing them inside the row loop.

─── django/contrib/admin/templatetags/admin_list.py:170-170 ───
[bug · medium] Deriving the header id from `slugify(text)` doesn't guarantee uniqueness or a
non-empty value:
- two columns can share the same label (e.g. `list_display = ["name", "parent__name"]`, or two
callables with the same `short_description`) → duplicate ids;
- a non-ASCII verbose name (e.g. `verbose_name = "名前"`) slugifies to `""` → an empty id, and
`aria-labelledby=""` on the list-editable widget then references nothing.
Consider building the id from the (unique) `field_name` instead, e.g. `"id_%s" %
slugify(_coerce_field_name(field_name, i))` or `slugify(field_name)`, so each header id is unique
and non-empty, and use the exact same value for the widget's `aria-labelledby`.

-             "id": slugify(text),
+             "id": slugify(_coerce_field_name(field_name, i)),


─── django/contrib/admin/templates/admin/change_list_results.html:21-21 ───
[bug · high] `header.id` only exists on the *sortable* branch of `result_headers()`. The other two
yields (the non-sortable branch and the `action_checkbox` branch) don't include an `id` key, so the
template renders `id=""` for them. Since actions are enabled by default, nearly every changelist
ends up with several `<div class="text" id="">` elements — invalid HTML (ids must be unique and
non-empty) — and for list_editable columns excluded via `sortable_by`, the widget's new
`aria-labelledby` would point to a non-existent id. Either guard the attribute here, or (better)
make `result_headers()` always emit an `id` (and derive it from the field name to guarantee
uniqueness / non-empty values, since `slugify()` returns `''` for non-Latin verbose names and
collides for duplicate labels).
